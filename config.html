claude code / settings

Config Notebook

Claude Code の設定は1つのファイルではなく、複数のファイル(スコープ)に分かれて置かれ、同じキーが重複したときに「どれが勝つか」の優先順位を持つ。公式ドキュメント code.claude.com/docs/en/settings は網羅的だが、階層の全体構造は文章だけではイメージしにくい。

本ページはその階層を図解し(§1・§2)、実際に複数スコープの設定を重ねたときの画面(/status の Setting sources、permissions の allow / ask / deny の各挙動)を端末実測で記録する(§3)。実測はまだ行っておらず、§3 のキャプチャ枠はすべて「未採取」のプレースホルダである。姉妹ページの Slash Command Notebook と同じ形式・同じ採取手順を使う予定。

§1設定の階層と優先順位

設定は5つの層が積み重なって解決される。上の層ほど強く、同じキーが複数の層にあるときは上の層の値が採用される。最上位の Managed settings は組織が配布するポリシーで、ユーザー側の設定では上書きできない。

強い 弱い
1 Managed settings 上書き不可

組織(管理者)が配布するポリシー。以下より下の層では上書きできない。

Linux: /etc/claude-code/managed-settings.json

macOS: /Library/Application Support/ClaudeCode/managed-settings.json

Windows: C:\ProgramData\ClaudeCode\managed-settings.json

2 CLI 引数

--model などの起動フラグ。その起動のみ有効。

3 プロジェクト・個人用(local)

.claude/settings.local.json

個人の実験・ローカル事情。Claude Code が自動で .gitignore に追加する。

4 プロジェクト共有

.claude/settings.json

チームで共有する設定。コミットする。

5 ユーザー全体

~/.claude/settings.json

全プロジェクトに効く個人のデフォルト。

同じキーが複数スコープにあるときは上の層が勝つ。→ §3 で実測予定(現在は未採取)。

§2どのファイルに何を書くか

§1 の各層のうち、自分で編集するのは settings.json 系の3ファイル。どこに書くかは「誰に効かせたいか」「git に載せてよいか」で決まる。

スコープパスgit 管理典型用途
ユーザー全体 ~/.claude/settings.json 対象外(ホーム直下) 個人のデフォルト。model、全プロジェクト共通の permissions・env など
プロジェクト共有 .claude/settings.json コミットする チームで揃えたい設定。プロジェクトの permissions ルール、hooks など
プロジェクト・個人用 .claude/settings.local.json しない(Claude Code が自動で .gitignore に追加) 個人の実験・ローカル環境の事情による一時的な上書き
Managed(組織) /etc/claude-code/managed-settings.json など(OS 別。§1 参照) 対象外(管理者が配布) 組織ポリシーの強制。ユーザー側では上書き不可

コラム — 紛らわしいファイルの区別

  • ~/.claude/settings.json — 本ページで扱う設定本体(ユーザースコープ)。
  • ~/.claude.json — 別物。ユーザースコープの MCP サーバー登録や CLI の状態が入る。settings 階層の一部ではない。
  • .mcp.json — プロジェクトで共有する MCP サーバー定義。これも settings とは別ファイル。
  • CLAUDE.md 系(~/.claude/CLAUDE.md・./CLAUDE.md)— これらは「メモリ」(モデルに渡る指示文)であり、settings ではない。

Setup

work/config-demo/

採取用フィクスチャ(構成のみ確定)

§3 の各セルは、この最小フィクスチャに対して採取する予定。

model キーを User / Project / Local の3スコープに別々の値で置き、優先順位の解決を観察できるようにする。permissions はプロジェクト共有の settings.json にだけ置き、allow(確認なしで実行)・deny(拒否)・ルール外(確認プロンプト)の3挙動を1つのフィクスチャで再現する。

work/config-demo/
├── src/hello.py                # print("hello from config-demo") のみ
├── secrets/credentials.env     # ダミー値 DUMMY_TOKEN=xxxx
└── .claude/
    ├── settings.json           # プロジェクト共有(下記)
    └── settings.local.json     # { "model": "claude-haiku-4-5" }
.claude/settings.json(プロジェクト共有) 
{
  "model": "claude-sonnet-5",
  "permissions": {
    "allow": ["Bash(python3 src/hello.py)"],
    "deny": ["Read(./secrets/**)"]
  }
}

§4主要キー早見表

settings.json のトップレベルキーのうち主要なもの。キー一覧は CLI バージョンで変わるため網羅はせず、完全な一覧は公式ドキュメントを参照(2026-08-20 時点)。

キー意味
permissionsツール実行の allow / ask / deny ルール、additionalDirectories(追加の作業ディレクトリ)、defaultMode(既定の権限モード)。→ ルール記法は下記
hooksツール実行の前後などのタイミングで任意のコマンドを実行する
envセッションに適用する環境変数
model既定で使うモデル
availableModels切り替え候補として提示するモデルの一覧
statusLineステータスラインのカスタム表示
outputStyle応答の出力スタイル
apiKeyHelperAPI キーを生成・取得するスクリプトの指定
cleanupPeriodDaysローカルデータの保持日数
autoUpdatesChannel自動更新のチャンネル
defaultShellBash ツールで使うシェル
companyAnnouncements起動時に表示する組織のアナウンス

permissions のルールは ツール名(パターン) の形式で書く。例: Bash(npm run test:*)(npm run test 系のコマンドを許可)、Read(./secrets/**)(secrets 配下の読み取りを対象に)。同じ記法を allow / ask / deny のどの配列に入れるかで挙動が変わる — 一致時の実際の画面は §3 の allow セル・ask セル・deny セルで実測予定(未採取)。

取得方法(予定)

  • 採取は ./capture-config.sh で行う予定: work/config-demo に §3 Setup のフィクスチャを構築し、tmux の仮想端末(110×42)で対話モードを起動して、各画面を tmux capture-pane -e で ANSI カラー付きテキストとして採取する。
  • 採取後、python3 ansi2html.py config で本ページの「(未採取)」枠を実測キャプチャに差し替える(term-bar のラベルで枠を特定する)。
  • 注意: capture-config.sh は採取中に一時的に ~/.claude/settings.json を変更し、終了時に復元する。普段使いの環境を汚さないよう、コンテナ等の隔離環境での実行を推奨。
  • 実測が済んだら、ヘッダの「実測 0/6 セル(準備中)」チップと各セルの「未採取 · 準備中」の日付印を実測日に更新する。
  • それまでの本ページの記述は公式ドキュメント(2026-08-20 参照)に基づくもので、画面・挙動の記述はすべて「期待される動き」であり実測値ではない。
