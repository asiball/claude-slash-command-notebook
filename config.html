claude code / settings

Config Notebook

Claude Code の設定は1つのファイルではなく、複数のファイル(スコープ)に分かれて置かれ、同じキーが重複したときに「どれが勝つか」の優先順位を持つ。公式ドキュメント code.claude.com/docs/en/settings は網羅的だが、階層の全体構造は文章だけではイメージしにくい。

本ページはその階層を図解し(§1・§2)、実際に複数スコープの設定を重ねたときの画面(/status の Setting sources、permissions の allow / ask / deny の各挙動)を端末実測で記録する(§3)。§3 の 16 画面は 2026-08-23 に Claude Code 2.1.241 で採取したもの(採取手順は取得方法)。姉妹ページの Slash Command Notebook と同じ形式・同じ採取手順を使っている。

§1設定の階層と優先順位

設定は5つの層が積み重なって解決される。上の層ほど強く、同じキーが複数の層にあるときは上の層の値が採用される。最上位の Managed settings は組織が配布するポリシーで、ユーザー側の設定では上書きできない。

強い 弱い
1 Managed settings 上書き不可

組織(管理者)が配布するポリシー。以下より下の層では上書きできない。

Linux: /etc/claude-code/managed-settings.json

macOS: /Library/Application Support/ClaudeCode/managed-settings.json

Windows: C:\ProgramData\ClaudeCode\managed-settings.json

2 CLI 引数

--model などの起動フラグ。その起動のみ有効。

3 プロジェクト・個人用(local)

.claude/settings.local.json

個人の実験・ローカル事情。Claude Code が自動で .gitignore に追加する。

4 プロジェクト共有

.claude/settings.json

チームで共有する設定。コミットする。

5 ユーザー全体

~/.claude/settings.json

全プロジェクトに効く個人のデフォルト。

同じキーが複数スコープにあるときは上の層が勝つ。→ §3 で実測(3スコープに別々の model を置くと、最上位の local の値が /status に出る)。

§2どのファイルに何を書くか

§1 の各層のうち、自分で編集するのは settings.json 系の3ファイル。どこに書くかは「誰に効かせたいか」「git に載せてよいか」で決まる。

スコープパスgit 管理典型用途
ユーザー全体 ~/.claude/settings.json 対象外(ホーム直下) 個人のデフォルト。model、全プロジェクト共通の permissions・env など
プロジェクト共有 .claude/settings.json コミットする チームで揃えたい設定。プロジェクトの permissions ルール、hooks など
プロジェクト・個人用 .claude/settings.local.json しない(Claude Code が自動で .gitignore に追加) 個人の実験・ローカル環境の事情による一時的な上書き
Managed(組織) /etc/claude-code/managed-settings.json など(OS 別。§1 参照) 対象外(管理者が配布) 組織ポリシーの強制。ユーザー側では上書き不可

コラム — 紛らわしいファイルの区別

  • ~/.claude/settings.json — 本ページで扱う設定本体(ユーザースコープ)。
  • ~/.claude.json — 別物。ユーザースコープの MCP サーバー登録や CLI の状態が入る。settings 階層の一部ではない。
  • .mcp.json — プロジェクトで共有する MCP サーバー定義。これも settings とは別ファイル。
  • CLAUDE.md 系(~/.claude/CLAUDE.md・./CLAUDE.md)— これらは「メモリ」(モデルに渡る指示文)であり、settings ではない。

§3実測デモ

以下は capture-config.sh で採取したシナリオ(2026-08-23、Claude Code 2.1.241、tmux 110×42。スタイル比較のみ 110×60)。3スコープ(User / Project / Local)に別々の設定を置いたフィクスチャに対し、優先順位の解決、permissions の allow / ask / deny の3挙動、権限モードの表示、Output style の選択と効果を画面で確認した。対話セルの画面は起動バナーを省き、該当プロンプト以降を載せている。メールアドレス・セッション ID・ホームディレクトリのパスは伏せ字。

Setup

work/config-demo/

採取用フィクスチャ · capture-config.sh が毎回再構築

§3 の各セルは、この最小フィクスチャに対して採取した。

model キーを User / Project / Local の3スコープに別々の値で置き、優先順位の解決を観察できるようにする。permissions はプロジェクト共有の settings.json にだけ置き、allow(確認なしで実行)・deny(拒否)・ルール外(確認プロンプト)の3挙動を1つのフィクスチャで再現する。

work/config-demo/
├── src/hello.py                # print("hello from config-demo") のみ
├── secrets/credentials.env     # ダミー値 DUMMY_TOKEN=xxxx
└── .claude/
    ├── settings.json           # プロジェクト共有(下記)
    └── settings.local.json     # { "model": "claude-haiku-4-5" }
.claude/settings.json(プロジェクト共有) 
{
  "model": "claude-sonnet-5",
  "permissions": {
    "allow": ["Bash(python3 src/hello.py)"],
    "deny": ["Read(./secrets/**)"]
  }
}

ユーザー設定 ~/.claude/settings.json には採取時のみ "model": "claude-opus-5" をマージする(採取後に復元)。権限モードと Output style のセルでは、この local ファイルに permissions.defaultMode や outputStyle を足した版で起動し直している。実測結果: model は3スコープのうち最上位の local が勝って claude-haiku-4-5 になり、/status の Setting sources には User / Shared project / Project local の3つが並んだ(下の /status セル)。
